## 一、空白骨架

````markdown
---
title: 文章标题写在这里
tags: [标签一, 标签二]
excerpt: 一句话说清这篇讲什么、读完能得到什么。
image: 
---

开头一段，直接说问题或结论，不要铺垫背景。读完这段，读者应该知道要不要继续读。

## 第一节：概念或背景

先说结论，再给原因。

- 要点一
- 要点二

## 第二节：怎么做

步骤或示例。代码给最小可运行版本：

```typescript
const store = getBlobStore("blog-articles");
const article = await store.get(id);
```

## 第三节：坑与边界

什么情况下这个方案不适用，以及失败了会怎样。

> 需要强调的结论放引用块里，会渲染成可复制的样式。

## 收尾

一句话总结，加一句下一步该看什么。
````

## 二、带 Frontmatter 的完整示例

下面这篇是格式正确的样例，可以拿来对照结构：

````markdown
---
title: 用 Netlify Blobs 存文章：不建数据库的内容方案
tags: [Netlify, 架构]
excerpt: 个人博客不需要数据库。这篇讲清用 Blobs 存文章、图片与设置时，索引该怎么设计、缓存该在哪里收口。
image: 
---

静态站最大的别扭之处是「想改一句话就得重新部署」。把文章从仓库挪到 Blobs 之后，写作和发布就彻底分开了：保存即生效，部署只负责前端。

代价是你得自己管一层索引。

## 数据分成两层

Blobs 是按 key 取值的存储，不是表。所以结构上只有两件事：

- **索引**：一条记录包含全部文章的元信息（标题、日期、标签、状态、字数）
- **正文**：按文章 id 单独存，只有进入阅读页才取

列表页只需要索引，所以首页一次请求就能渲染完整卡片墙。

## 索引的写入必须收口

索引是唯一的真相来源，一旦两边写入就会不一致。做法是只留一个入口：

```typescript
async function saveArticleIndex(store: Store, index: ArticleMeta[]) {
  await store.set("index", JSON.stringify(index));
}
```

- 新增、改标签、发布、下架，全部走同一个函数
- 单个文章的正文与索引分两次写，先写正文再写索引，避免索引指向不存在的正文

## 代价是缓存

Blobs 读不算慢，但列表页每次都全量拉索引并不划算。所以缓存要收口在两处：

- 服务端对索引接口加 Cache-Control，并提供一个主动失效的刷新接口
- 前端首页缓存 60 秒，发布后不立刻可见属于预期行为

> 如果读者抱怨「发了看不到」，先确认状态是已发布，再等 60 秒。这不是 bug。

## 收尾

Blobs 适合「读多写少、结构简单、单作者」的场景：省掉一个数据库，也省掉同步部署的等待。但当文章量到几千篇、需要全文检索和复杂排序时，就该换成真正的数据库了。
````

## 三、模板使用提示

| 情况 | 怎么改 |
|------|--------|
| 短随笔（<1500 字） | 只留导语 + 2 个 H2 + 收尾 |
| 教程类 | 每节结尾加一句「做到这里应该看到什么」 |
| 踩坑记录 | 顺序改成「现象 → 排查 → 原因 → 修法」 |
| 系列中的一篇 | 导语里点明是第几篇，收尾指向下一篇 |
| 需要图 | 在对应小节后加 `![图注](地址)`，图注写清图里是什么 |

更多可粘贴指令见 [06-提示词模板](./06-提示词模板.md)。
