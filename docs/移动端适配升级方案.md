### 手机端硬伤（已在代码中逐条确认，优先级最高）

以下按页面分组：**文章页-1~4**、**后台-1~4**、**首页-1~6**。每条都标注了确切文件与行号，可直接逐条施工与验收。

#### 文章页-1. 超宽表格 / 长代码行在手机上完全看不到右半部分

这是本次审查发现的最严重问题，三处代码叠在一起导致死角：

1. `public/css/scrollbar.css:74-79` 用 `overflow-x: hidden !important` 直接**禁止**了 `.article-content pre` 与 `.article-content table` 的横向滚动；
2. 同文件 `80-87` 再把它们的滚动条 `display: none`；
3. 原本用来兜底的「按住左右拖动查看」实现（`public/js/article-app.js:1560-1598`）**只监听了 `mousedown` / `mousemove` / `mouseup`，没有任何触摸事件**。

结果：手机上遇到 3 列以上的表格或超长代码行，**没有任何手段能看到右侧内容**。这是硬阻断，不是体验问题。

修复方向（保留原本「桌面端无滚动条、可拖动」的设计意图）：

```css
/* scrollbar.css 末尾追加：只在触屏设备上恢复横向滚动能力 */
@media (hover: none), (pointer: coarse) {
    .article-content pre,
    .article-content table {
        overflow-x: auto !important;
        scrollbar-width: thin !important;
        -ms-overflow-style: auto !important;
    }
    .article-content pre::-webkit-scrollbar,
    .article-content table::-webkit-scrollbar {
        display: block !important;
        height: 6px !important;
    }
    .article-content pre::-webkit-scrollbar-thumb,
    .article-content table::-webkit-scrollbar-thumb {
        background: rgba(255, 255, 255, .3) !important;
        border-radius: 99px !important;
    }
}
```

```js
// article-app.js:1567 把鼠标事件换成 pointer 事件，鼠标拖拽行为保持不变
document.addEventListener('pointerdown', function (e) {
    const t = e.target && e.target.closest
        ? e.target.closest('.article-content table, .article-content pre') : null;
    if (!t || t.scrollWidth <= t.clientWidth + 1) return;
    if (e.pointerType === 'touch') return;   // 触摸交给原生横滑，避免抢走纵向滚动
    scroller = t; startX = e.clientX; startScroll = t.scrollLeft; moved = false;
});
```

同时给 `.article-content pre` / `table` 补 `touch-action: pan-x pan-y`，并给表格右边缘加渐隐蒙版暗示「还有内容」。

#### 文章页-2. 聊天窗在 iOS 上被键盘遮住

`style.css:2623-2635` 在 `≤480px` 把聊天窗设为 `height: 100vh !important`，而 `chat.js` 全文没有任何 `visualViewport` / `dvh` 处理。iOS 键盘弹出时 `100vh` 不缩小，输入框与发送键被键盘完全盖住——用户打字看不见自己写的内容。修法与建议 2、建议 10 合并处理（`--vvh` 变量 + `env(safe-area-inset-bottom)`）。

#### 文章页-3. 弱网下文章页看起来是白屏

`animations.js:95-98` 在 DOMContentLoaded 就给 `.article-header`、`.article-content`、`.reader-toolbar` 打上 `data-reveal`，而 `glass.css:349-358` 对该属性的定义是 `opacity: 0` + `blur(12px)`。此时 `article.html` 里放的正是「加载文章中…」的转圈提示——**加载提示自己被隐藏了**。正文要等 `/api/admin?action=articles` 返回才渲染，弱网/冷启动时用户看到的是一个只有 3px 进度条的空白页。

修复（二选一或同时）：

```css
/* glass.css 追加：加载态 / 错误态不参与入场隐藏 */
html.glass-ready [data-reveal]:has(.loading-article),
html.glass-ready [data-reveal]:has(.error-state) {
    opacity: 1; transform: none; filter: none;
}
```

```js
// animations.js mark() 里加守卫，加载占位不打 data-reveal
if (el.querySelector('.loading-article')) return;
```

#### 首页-1. 底部内容在 iPhone 上永久滚不出来（最隐蔽的一条）

`style.css:37-40` 是 `body.home-layout { overflow: hidden; height: 100vh }`，`46-57` 的 `.content-wrapper` 同样 `height: 100vh`，滚动交给内部的 `#scrollArea`（`384-389`）。`100vh` 在移动浏览器里等于**地址栏收起后的大视口高度**，但 body 本身不滚动、地址栏永远不会收起——于是 `#scrollArea` 底部约 50–90px（最后几张卡片 + `.footer` 里的 RSS / About）**恒定为不可达区域**。

这不是「体验差」，是页脚链接在 iPhone 上根本点不到。修法：

```css
body.home-layout { overflow: hidden; height: 100vh; height: 100dvh; }
.content-wrapper  { height: 100vh; height: 100dvh; }
```

旧 iOS（< 15.4）不认 `dvh`，补一条 `visualViewport` 兜底即可（`--app-h` 变量）。

#### 首页-2. 手机上没有「内容形态筛选」入口

`style.css:1673-1675` 在 `≤600px` 把 `.nav-links` 直接 `display: none`，而它承载的是**全部 / 文章 / 白板 / 随记 / 导图**五个形态筛选（`index.html:46-52`，逻辑在 `app.js:467-472`）。

首页**没有**文章页那种悬浮球，剩下的「标签」按钮走的是 `filterByTag`（`app.js:460-464`）——**和形态筛选是两条互斥路径，无法互相替代**。所以手机上「只看白板」「只看随记」「只看导图」彻底不可达。

好消息是 `.nav-links` 本身已经有 `overflow-x: auto` + 隐藏滚动条（`style.css:198-212`），**不需要新建抽屉组件**，只要不 `display:none`：

```css
@media (max-width: 600px) {
    .nav-links { display: flex; flex: 1; min-width: 0; gap: 18px;
        overflow-x: auto; padding-bottom: 6px; -webkit-overflow-scrolling: touch; }
    .nav-link { flex: none; padding: 12px 2px; }
    .nav-inner { justify-content: space-between; }
}
```

如果更想要「底部抽屉式筛选」，那也建议复用同一个组件规范，别和文章页悬浮球各写一套（见建议 6）。

#### 首页-3. 旋转屏幕后所有封面被拉伸变形

`app.js:1019-1034` 的 `handleCoverLoad()` 只在图片 `onload` 时读一次 `box.clientWidth`，把高度**写死成内联 px**（`1030`），并把 `objectFit` 设成 `fill`（`1032`）。竖屏 375px 算出的高度，转到横屏 667px 时宽度翻倍而内联高度不变 → 图片被横向拉扁。全站唯一的 `resize` 监听（`app.js:1301-1303`）只重排了指示器，不重算封面。

首选修法是彻底不用内联高度：

```css
.card-img { aspect-ratio: 16 / 10; }
.card-img .img-placeholder { width: 100%; height: 100%; object-fit: cover; }
```

顺带解决另一个问题：`app.js:1028-1030` 的注释明说「不再夹取区间：卡片多长都行」，于是一张 1080×1920 的竖封面在 375px 视口下被算成 351×**624px**——一屏只剩一张图，且 `onload` 时把 180–280px 的占位高度改成 624px，正是 CSS 注释想避免的 CLS。移动端建议加 `maxRatio` 上限（如 1.4）。

#### 首页-4. 灯箱会一次预加载 4 张原图

`index.html:285-303` 的 `preloadGalleryImage` + `preloadGalleryNeighbors` 会预取当前图 ±2 共 **4 张原图**（调用点 `index.html:351`、`384`）。手机 4G 上打开灯箱瞬间多下几 MB，弱网就是几秒白屏。项目其实已经有缩略图通道（`app.js:688-710` 的 `/images/t/` 归一化，图库网格已在用 `img.thumb`），只需：

```js
// 移动端 + 慢网不预取相邻原图
const cheap = navigator.connection && !/4g/i.test(navigator.connection.effectiveType || '4g');
if (window.innerWidth <= 600 && cheap) return;
```

同时卡片封面（`app.js:296-303`）目前是原图、无 `srcset/sizes`，应优先用 `?w=` 通道——这是首页流量最大的单点，比 JS 体积更致命。

#### 首页-5. `prefers-reduced-motion` 在页面内联动画处全部漏判

CSS 层（`glass.css:520-545`）和 `animations.js:13-20` 的门控都做得很好，但**直接在页面里调用的 `anime.animate` 全部没有判断**：`index.html:357-361`（灯箱打开）、`390-394`（翻页）、`449-452`、`460-461`（留言图灯箱）、`app.js:637-639`（视图切换）、`992-1001`（新闻列表）、`1092-1100`（仪表盘）。

开了「减少动效」的用户在手机上切视图、开灯箱仍有整套位移+缩放动画。抽一个 helper 过一遍即可：

```js
window.anim = (el, params) => {
    if (window.BlogAnimations && BlogAnimations.ready && typeof anime !== 'undefined') anime.animate(el, params);
};
```

#### 首页-6. 几十张卡片的 `backdrop-filter` 是低端机掉帧的主因

`glass.css:139-146` 每张 `.card` 都带 `backdrop-filter: blur(22px) saturate(170%)`，图库项 `blur(16px)`（`176-182`），另有 `.aurora-orb` 的 `blur(90px)` + 26s 无限动画（`40-49`）并带 `will-change`。首页一次渲染几十上百张卡片，每张都要实时模糊背后内容——这是移动 GPU 最贵的属性。`animations.js:47-53` 已经在移动端把光斑从 4 个减到 2 个（方向对），但 blur 与常驻动画没减。

```css
@media (hover: none), (max-width: 900px) {
    .card, .gallery-item, .dash-hero, .dash-panel, .dashboard-card,
    .top-bar, .nav-bar, .search-dropdown {
        backdrop-filter: none !important;
        -webkit-backdrop-filter: none !important;
    }
    .card { background: rgba(255, 255, 255, .055) !important; }
    .aurora-orb { animation: none; will-change: auto; filter: blur(70px); }
}
```

同理 `.article-content`（`glass.css:307-313`）覆盖整篇长文，滚动时反复重采样，手机上也要关掉。

#### 后台-3. 其余可直接修的项

- **排序模式的拖拽是唯一刚需**：改成上下箭头按钮（该模式已有批量工具条可复用）。
- **浮动操作条的层级冲突**（`admin.html:38-46`，`z-index:160`）：与 `#fpMask`（`1651`，同层级）靠 DOM 顺序决胜负，预览抽屉打开时可能浮在遮罩之上；`.toast`（`203`，`bottom:24px`）也与它重叠。浮动条提到 `z-index:200`，toast 移到 `bottom:76px` 居中。
- **图片灯箱的翻页按钮压在图片边缘 8px 处**（`admin.html:497-499`），想放大看细节就会翻页；挪到图片下方的独立操作行。
- **登录态只靠 `localStorage` 且无 try/catch**（`admin-app.js:5`）：iOS 无痕模式下 `localStorage` 会抛 `SecurityError`，**整个 `admin-app.js` 不执行、页面白屏**。加 `safeGet/safeSet` 包装。
- **401 无分支**（`admin-app.js:49` 的 `loadArticles` 无 catch / 无 401 判断）：手机切回后台（页面被系统回收后重载、key 已被 ITP 清掉）时，用户看到的是空白列表而不是登录页，只会以为「文章没了」。
- **`displayUrl()` 把管理密钥写进图片 URL query**（`admin-app.js:43`）：密钥会进入 DOM、浏览器历史、Referer 和中间缓存日志；手机流量常经运营商代理，风险更高。建议改短期签名。
- **`admin.html` 没有引入 `style.css`**（只引了 `glass.css` / `scrollbar.css` / `responsive.css`，见 `760-762`），却使用了 `--bg-tertiary`、`--text-primary`、`--text-secondary`、`--shadow`、`--glass-border`——这些变量只在 `style.css:3-8` 定义。结果 `.art-search`、`.ac-title` 等元素回退到初始值（透明/继承），**暗色模式下卡片与页面同色、层级感丢失**。在 `admin.html:17` 的 `:root` 里补齐这几个变量即可。
- **拖拽排序/H5 drag 在手机上完全不触发**（见 E3），`admin.html:1248` 的「拖拽上传/移入」提示在手机上是空头承诺。

#### 文章页-4. 内嵌白板在小屏占满一屏且难用

`article.html:734-744` 的 `.excalidraw-embed` 是 `height: 70vh; min-height: 420px`。375×667 视口下 70vh≈467px，一块白板几乎占满整屏，文章里若连续嵌两三块，滑动体验极差。建议窄屏降到 `height: 56vh; min-height: 320px; max-height: 480px`，并在白板上加一条「点开全屏查看」的入口——这与 `docs/思维导图模块-设计方案.md:136,189` 已确立的「移动端只做查看」原则一致。

#### 后台-1. 三条「点不动」的死路

后台的结构层适配其实做得比多数纯静态后台好（表格→卡片、底部 tab、抽屉面板、`dvh`），问题集中在**触摸语义**：

**E1. `:has()` 规则把 Vditor 的操作面板整条屏蔽**

`admin.html:607-609`（`admin-edit.html:164-166` 同）写着：

```css
html body .vditor-panel--none:has(button[data-type="remove"]) { display: none !important; }
```

本意是隐藏「点图片后弹出的浮动操作条」，但 `[data-type="remove"]` 同时出现在**图片、链接、表格行列操作**面板里——这些面板在窄屏下本来最需要，现在整条不渲染。这是行内编辑的硬阻断。建议删掉该规则，改为收窄内边距并放大按钮：

```css
html body .vditor-panel--none { padding: 4px 6px !important; }
html body .vditor-panel--none button { min-width: 34px; min-height: 34px; }
```

**E2. 只有 `:hover` 才出现的删除按钮，触屏上第一次点击无效**

`admin.html:164-165`（`.classify-card .cc-del`）、`200-201`（`.image-picker-item .picker-del`）、`284-285`（`.tags-card .tc-actions button`）都是 `opacity: 0` → `:hover` 变 1。手机第一次点击只会应用 hover 状态、不派发 click，用户必须点两次；在图片网格里会被理解成「按钮坏了」。作者只在 `.tags-card` 的 480px 断点打过补丁（`admin.html:509`），图片卡片漏了。

```css
@media (hover: none) {
    .classify-card .cc-del,
    .image-picker-item .picker-del { opacity: 1; width: 26px; height: 26px; font-size: 13px; }
}
```

**E3. 四套拖拽功能在手机上完全不存在**

`admin-app.js:150`（`<tr draggable="true">` 排序模式）、`2873` + `290-321`（图片分类拖动）、`1675-1724`（左右面板拖拽上传/移入）、`2965-2980`（设置卡片排序）全部依赖 HTML5 drag 事件，而触摸设备**根本不派发这些事件**。`admin.html:1248` 那句「拖拽上传/移入」在手机上是空头承诺。

最小代价的替代路径：排序模式改用上下箭头按钮（该模式已有批量工具条可复用），图片分类引导到已有的批量操作模式（`toggleBatchMode('left')`），设置卡片排序在移动端直接隐藏拖拽手柄。

#### 后台-2. iOS 表单聚焦自动放大（登录页第一屏就会踩到）

后台几乎所有输入控件字号都 < 16px：`.login-box input` 14px（`admin.html:23`）、`.settings-field input` 13px（`329`）、`.rename-box input` 14px（`370`）、`.publish-field` 13px（`730`）、`.exc-field` 13px（`412`）、`admin-edit.html:294` 13px、`tag-picker.js:40` 12px。iOS Safari 在 <16px 控件聚焦时会把整页放大到约 1.2 倍，**收起键盘后不会自动缩回**，后台布局被顶出视口。

推荐不牺牲可访问性的做法（不用 `maximum-scale=1`）：

```css
@media (max-width: 768px) {
    input, select, textarea { font-size: 16px !important; }
}
```

#### 后台-4. 编辑器高度在手机上会永久卡在下限

`admin-app.js:562-570` 的 `fitEditor()` 在 `wrap.clientHeight < 240` 时直接 return，兜底值是 `Math.max(360, content.offsetHeight - 300)`（`980-981`）。索引式切到「写文章」时 `#tab-write` 刚 `display:flex`、高度还是 0 → 编辑器永久停在 360px；再扣掉 Vditor 工具栏（25 个按钮，520px 以下每个 padding 加到 `0 12px`）和面板的 `padding-top:38px`，**真正能写字的区域不到 220px**。

修法：放宽阈值 + 切 tab 后强制重算（`requestAnimationFrame` + `setTimeout` 各一次），长期方案是用 `ResizeObserver` 替代 `clientHeight` 硬算：

```js
function fitEditor() {
    const h = wrap.clientHeight;
    if (h < 120) return;
    host.style.height = Math.max(320, h) + 'px';
}
```

### 其余缺口清单

1. **视口声明不完整**：`index.html:5`、`article.html:5`、`admin.html:5`、`admin-edit.html:5`、`excalidraw.html:5`、`mindmap.html:5` 均为 `width=device-width, initial-scale=1.0`，缺少 `viewport-fit=cover`（刘海屏安全区失效）。
2. **视口高度单位过时**：`style.css:39,50,1863,2629,2870,2875` 等 10+ 处使用 `100vh` / `calc(100vh - Npx)`，移动浏览器地址栏伸缩时会导致高度跳动 / 底部被裁。全项目 **零 `dvh` 使用**。
3. **安全区完全未适配**：全项目**零 `env(safe-area-inset-*)`**。右下角悬浮球（`article.html:1538`）、聊天窗、底部工具栏在全面屏手势条附近易被误触或遮挡。
4. **首页移动端筛选入口缺失**：`style.css:1673-1675` 在 `≤600px` 直接 `.nav-links { display: none }`，首页**没有**文章页那种悬浮球，而剩下的「标签」按钮走 `filterByTag`（与形态筛选互斥），因此「只看白板 / 随记 / 导图」在手机上不可达。详见上文「首页-2」。
5. **触摸反馈缺失**：零 `-webkit-tap-highlight-color` 控制、零 `:active` 触摸态、零 `touch-action` 声明。手机上点击无反馈，且双击缩放可能误触发。
6. **hover-only 交互在触摸下不可达**：`style.css:617,1184,1227,2258,2671`、`glass.css:422-423` 等一批 `.card:hover` / `.xxx:hover .yyy` 揭示元素，在触屏设备上永远不显示（或需要「第一次点击只当 hover」的两段式操作）。
7. **设计令牌缺失**：字号散落 150+ 处，其中 10px（`style.css:449,1657,2319,2667,2679`）、11px（`style.css:538,1270,1287,1316,2042,2171,2250,2428,2587,2685,2745`）在手机上明显偏小（iOS 可读性下限约 12px，正文建议 ≥16px）。断点 1400/1200/1024/900/773/768/700/600/480/460/360 混用，跳跃不平滑。
8. **无「跟随系统」主题**：`theme.js` 提供手动切换，但**零 `prefers-color-scheme` 使用**。手机上夜间访问白屏刺眼。
9. **零 PWA 支持**：无 `manifest.json`、无 Service Worker、无独立图标。`grep` 确认 `public/` 下不存在任何 manifest / sw 文件。

## 三、分阶段升级路线

### P0：基础设施补丁（低风险、改动小、立竿见影）

**建议 1：补齐 viewport 声明**

六个页面的 `<meta name="viewport">` 统一改为：

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
```

`viewport-fit=cover` 让 `env(safe-area-inset-*)` 生效，是后续安全区适配的前提。

**建议 2：视口高度全部换 `dvh`**

```css
/* 兜底：不支持 dvh 的旧浏览器回落到 vh */
.hero,
.article-layout,
.chat-window,
.page-shell {
    height: 100vh;
    height: 100dvh; /* 后写的覆盖前面的 */
}

/* calc 场景同理 */
.chat-window { height: min(520px, calc(100vh - 160px)); }
.chat-window { height: min(520px, calc(100dvh - 160px)); }
```

改造点集中在 `style.css:39,50,1863,2509,2519,2537,2629,2870,2875`，逐个加 `dvh` 覆盖行即可，不必删 `vh`（保留旧浏览器兜底）。

**建议 3：全局触摸基线**

在 `responsive.css` 顶部（或新建 `public/css/mobile.css`，各页 head 末尾引入）加：

```css
html {
    -webkit-text-size-adjust: 100%;  /* 横屏不自动放大字号 */
    text-size-adjust: 100%;
}

body {
    -webkit-tap-highlight-color: transparent;  /* 去掉安卓灰色高亮块 */
    overscroll-behavior-y: none;               /* 去掉橡皮筋回弹，更像 App */
}

/* 触摸设备：用 :active 提供即时反馈，替代不可用的 :hover */
@media (hover: none) and (pointer: coarse) {
    .card, .tag-btn, .nav-link, .toc-item, .chat-send {
        min-height: 44px;          /* 点击目标 ≥ 44×44 */
        min-width: 44px;
    }

    .card { touch-action: manipulation; }  /* 消除 300ms 双击缩放延迟 */

    /* hover-only 的隐藏元素在触屏上常态可见 */
    .card .card-actions,
    .chat-session-item .chat-session-del {
        opacity: 1;
        visibility: visible;
        pointer-events: auto;
    }

    .card:active { transform: scale(0.985); transition: transform 90ms ease-out; }
    .tag-btn:active { opacity: 0.85; }
}
```

这一步能一次性解决触摸反馈、点击目标、hover 不可达三个体验痛点。

**建议 4：安全区适配**

```css
:root {

/* 聊天输入框固定在底部时 */

```

### P1：交互结构补齐（体验提升最明显的一档）

**建议 6：补齐移动端筛选 / 导航入口**

首页 `.nav-links` 被隐藏导致形态筛选不可达（见上文「首页-2」，`.nav-links` 本身已支持横滑，改回 `display: flex` 即可，成本极低）。

若后续要统一移动端入口组件，推荐把文章页已有的悬浮球模式抽成独立文件 `public/js/mobile-menu.js`，首页、后台、导图页按页面配置引入，菜单项各自决定（首页：筛选 / 搜索 / 标签 / 主题 / RSS；文章页：目录 / 返回 / 首页 / 主题 / 专注 / AI 助手）。比「每页各写一个汉堡抽屉」更省事，也不会重复造组件。

**建议 7：触摸设备上的 hover-only 交互改造**

统一改造模式为「常显 + 触屏更显」，并给所有可点元素补 `:active`。涉及 `style.css:617,1184,1227,2258,2671` 与 `glass.css:422-423`。

**建议 8：字号体系收敛为设计令牌**

建立移动端字号下限，用 CSS 变量控制：

```css
:root {
    --fs-2xs: 12px;   /* 原 10px 类：标签、角标，说明性文字不允许低于 12px */
    --fs-xs: 13px;    /* 原 11–12px 类：meta 信息 */
    --fs-sm: 14px;
    --fs-base: 16px;  /* 正文：手机上不缩放 */
    --fs-lg: 18px;
}
```

然后按断点整体抬一档：

```css
@media (max-width: 600px) {
    :root { --fs-2xs: 12px; --fs-xs: 13px; --fs-sm: 15px; }
    .card-meta, .hero-stat-label, .card-desc { font-size: var(--fs-xs); }
    .article-content { font-size: var(--fs-base); line-height: 1.75; }
}
```

注意：表单输入框（`input` / `textarea` / `select`）在手机上**必须 ≥ 16px**，否则 iOS Safari 聚焦时会强制放大页面。目前多处输入框是 12–13px（如 `capsule.css:53,78,102,149`、`drawer.css:88`、`style.css:1715-1717`），需要单独处理：

```css
@media (max-width: 600px) {
    input, textarea, select { font-size: 16px; }
}
```

**建议 9：跟随系统主题**

`theme.js` 增加「自动」模式（三态：自动 / 亮 / 暗），默认自动：

```js
const mq = window.matchMedia('(prefers-color-scheme: dark)');
mq.addEventListener('change', () => {
    if (themeMode === 'auto') applyTheme(mq.matches ? 'dark' : 'light');
});
```

并在 `<head>` 内联一小段同步脚本，防止首屏白闪。

**建议 10：虚拟键盘遮挡处理**

文章页聊天窗（`chat.js`，`window.innerWidth <= 773` 分支见 `chat.js:337`）与后台编辑器在手机上聚焦输入框时，键盘会遮住输入框。用 `visualViewport` 修正：

```js
if (window.visualViewport) {
    window.visualViewport.addEventListener('resize', () => {
        const kb = window.innerHeight - window.visualViewport.height;
        document.documentElement.style.setProperty('--kb-offset', kb + 'px');
    });
}
```

```css
.chat-window.is-mobile-open { max-height: calc(100dvh - var(--kb-offset, 0px) - 24px); }
```

把 1400/1200/1024/900/773/768/700/600/480/460/360 这串混用断点统一为 4 档：`≤480`（手机竖）/ `481–768`（手机横 + 小平板）/ `769–1024`（平板）/ `>1024`（桌面）。同时把「卡片在当前容器里多宽」这类问题改用容器查询（`@container`），比视口查询更准确——`container-type: inline-size` 写在 `.waterfall` / `.article-main` 上即可。这属于结构性改造，建议单独排期。

**建议 12：vendor 体积治理**

- 确认 mermaid / mathjax / graphviz / echarts / lute 全部走「按需动态注入」路径，并在 `docs/` 里留一份「谁在什么时候加载什么」的对照表。

**建议 13：图片与图表在小屏降级**

- 首页卡片封面在手机上用更小的 `?w=` 变体（现有机制已支持，只需调整 `sizes`）。

**建议 14：PWA + 添加到主屏**

- `public/manifest.webmanifest`：`display: standalone`、`theme_color`、`background_color`、192/512 图标（可用现有 `web-logo.webp` 生成）。
- Service Worker：先只缓存静态资源（HTML 走 network-first，CSS/JS 走 cache-first，因为已带 `?v=`），不需要离线可用全部功能。
- 收益：手机上可全屏、可加桌面图标、二次打开秒开。

**建议 15：真机回归清单（每个阶段收尾必做）**

建议至少在以下环境实测，并把清单沉淀到 `docs/操作文档.md`：

| 环境 | 必查项 |
| --- | --- |

| 系统深色模式 | 主题是否跟随、首屏是否白闪 |

## 五、待确认事项

1. **是否引入构建步骤**？当前 `pnpm build` 只跑 `tsc --noEmit`。若要压缩 JS / 处理 CSS 变量，需要一个轻量 `esbuild` 步骤；好处是性能与可维护性，代价是部署链路变复杂、与「纯静态、打开即改」的现有习惯冲突。
2. **后台编辑器在手机上支持到什么程度**？`admin-edit.html` 用 Vditor（`MOBILE_WIDTH=520`），手机上编辑长文体验有限（工具栏吃 120px，可写区 < 220px）。是「能用就行」还是「只读 + 桌面端编辑」？
3. **Excalidraw / 导图在手机上是否开放编辑**？`docs/思维导图模块-设计方案.md:136,189` 的既定原则是只读查看，需确认是否维持。
4. **PWA 是否需要离线能力**？只做「添加到主屏 + 缓存静态资源」是最小改动；完整离线需重新设计数据层缓存。
5. **拖拽排序在手机上的替代交互**：上下箭头按钮（成本最低）还是长按拖动（更现代但要新写手势）？
6. **后台管理密钥的传递方式**：是否要改短期签名？现方案把密钥放在图片 URL query（`admin-app.js:43`），会进入历史 / Referer / 中间缓存日志。

## 六、三份专项审查的边界说明

本文档整合了首页、文章页、后台三份只读代码审查的结论。以下为**已被证伪或需要澄清**的判断，避免后续误改：

- 首页**不存在** hover 独占的操作，所有 hover 效果均为纯装饰（预取与 `title` tooltip 除外），这点做得很好。
- 「mermaid / mathjax 被无条件加载」**不成立**：`index.min.js` 内部确实按内容懒加载这些子包；只有 `admin-edit.html:10-11` 是无条件同步引入 Vditor 主体。
- `responsive.css:13-15` 用 `overflow-x: clip` 而非 `hidden` 是**正确选择**（不创建滚动容器、不破坏 sticky），但 `clip` 需要 Safari 16+ / Chrome 90+，老引擎上该层兜底失效，建议补 `@supports not (overflow: clip)` 降级。
- 首页 `.card { opacity: 0 }`（`style.css:1146-1148`）**没有** JS 门控（不像 `[data-reveal]` 有 `html.glass-ready` 保护），脚本异常时首页会整片空白，建议对齐 `[data-reveal]` 的写法。
- 首页**没有**加载 `chat.js`，因此 `style.css:1826-2640` 的聊天窗样式在首页是死代码（不影响功能，只影响体积）。
