## 一、目标定位

**产品定位（已确认）**：

> 写文章时**可以随意插入**白板、思维导图；读者**在文章里就能看到**它们；
> 白板/导图是**文章讲解时提高理解的工具**，而不是与文章并列的独立工具。
> 但只用其中一个时，**也要能当独立工具使用**。

由此得到一个统一模型——**三态收敛为「一个文章，可选挂载」**：

| 形态 | 数据表达 | 阅读页表现 |
| --- | --- | --- |
| 纯文章 | `type:article`，正文 Markdown | 现有阅读页（目录 / 进度条 / 评论） |
| 纯白板 | `type:whiteboard` + `boardId`，正文空 | 整页画布（`board-mode`，已实现） |
| 纯导图 | `type:mindmap` + `mapId`，正文空 | 整页导图（已实现） |
| **混排（本次新增）** | `type:article`，正文**内嵌若干白板/导图** | 阅读页顺序内联 |

**关键判断**：混排**不需要新的 `type`**。它就是 `article`，只是正文里多了嵌入块。

**因此本方案是纯加法**：

- 不改现有三态的数据结构
- 不新增 `type` 枚举值
- 现有 `boardId` / `mapId` 继续承担「整页形态」的关联，正文 fence 承担「混排引用」
- 纯白板 / 纯导图的独立发布路径**完整保留**

## 二、为什么引用必须放在正文里（不可绕过的约束）

### 2.1 Vditor 只认 Markdown

编辑器用 `vditor.getValue()` 取正文（`admin-edit.js:192`、`admin-app.js:1052`），提交的是**纯 Markdown 文本**。

因此内嵌协议**必须是合法 Markdown**。自定义 HTML 标签在 wysiwyg 模式下会被当作内容/转义（`admin.html` Vditor 配置为 `mode:'wysiwyg'`，见 `admin-app.js:986`、`admin-edit.js:141`，**没有任何 sanitize / renderers 配置允许自定义 HTML 块**）。

这也是历史设计选择 fenced code 而非 `:::note` 或 HTML 注释的原因（`docs/讨论.md` 约 426-431 行）。

### 2.2 `boardId` / `mapId` 是互斥单值

`admin.ts:280-285` 明确：

```ts
const boardId = type === "whiteboard" && ... ? ... : ""
const mapId   = type === "mindmap"    && ... ? ... : ""
```

只有 `type` 匹配时才保留对应 id。**一篇文章同时挂一张白板 + 一张导图，在当前数据模型下无法表达。**

→ 结论：**混排引用必须走正文 fence，不能复用 `boardId` / `mapId`。**

### 2.3 两条解析管线（最大的隐藏坑）

| 路径 | 触发条件 | 是否含自定义 renderer |
| --- | --- | --- |
| 主线程 `MarkdownParser.parseMarkdown()`（`markdown.js:66-147`） | `content.length < 5000` | ✅ 有 `renderer.code` / `renderer.image` / `==高亮==` 扩展 |
| Web Worker（`markdown-worker.js:5-11`） | `content.length >= 5000`（`markdown.js:152`） | ❌ **只 `importScripts(marked)` + `marked.parse`，没有任何自定义 renderer** |

**后果（现存缺陷，非本方案引入）**：≥5000 字的文章里，`renderer.code` 不生效 → 产出的 `<pre><code>` 没有 `.code-block` 包裹 → `article-app.js:635` 的 `.code-block code.language-excalidraw` 匹配不到 → **现有白板内嵌在长文里静默失效，显示成一段代码**。同时 `==高亮==`、图片 figure / 懒加载 / URL 重写也一并失效。

→ 任何基于「自定义 renderer 输出特殊标记」的方案，都必须先统一这条管线，否则长文短文行为不一致。**这是本方案的第一前提。**

## 三、核心设计：内嵌语法

### 3.1 语法定义

复用现有 fence 机制，泛化为带 `kind:` 前缀的统一语法：

````markdown
正文段落……

```embed board:wb-abc123
```

```embed map:mm-xyz789 :h=520 :caption="登录流程"
```
````

**兼容性**：裸 ```` ```excalidraw ```` 继续被识别（等价于 `board:`），**现有文章不会坏**。新语法是它的泛化。

### 3.2 参数

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `:h=<像素>` | 桌面 480 / 手机 60vh | 内嵌块高度，允许单块覆盖 |
| `:caption="文本"` | 空 | 块下方的图注 |
| `:title="文本"` | 取画布自身标题 | 块上方标题（可选） |

选择 `:key=value` 而非 JSON，是为了在 Vditor 里手写和阅读都不痛苦。

### 3.3 高度策略（已确认）

- **桌面默认 480px**
- **手机默认 60vh**（内嵌白板原来的 `70vh` 在手机上占满一屏，已在移动端方案中记录为问题）
- **单块可用 `:h=` 覆盖**

```css
/* 目标形态，示意 */
.embed-block { height: 480px; }
@media (max-width: 773px) { .embed-block { height: 60vh; } }
```

### 3.4 内嵌导图的交互深度（已确认：A + B）

| 能力 | 说明 |
| --- | --- |
| **A. 只读查看** | 缩放、折叠节点、看备注与节点图片；点节点不跳转 |
| **B. 跳转编辑** | 块浮条提供「在导图页打开」→ 新窗口打开 `/mindmap.html?note=<id>&edit=1`；若该导图有敏感操作，跳转前提示未保存状态由导图页自行处理 |
| ~~C. 原地编辑~~ | **明确不做**：内嵌态直接改会让「文章页」变成第二套编辑器，复杂度陡增且与 `#view-mindmap` 重复 |

导图内嵌走 **iframe**，复用现成页面，**零新增 bundle 体积**：

- `mindmap.html:532` 已有「被 iframe 嵌入」检测（`document.documentElement.dataset.embedded = '1'`，用于隐藏胶囊只留导出）
- 参数化模式与项目现有习惯一致（`mindmap.html:512-529` 已用 `note` / `edit` 参数；`excalidraw.html` 用 `from=admin` / `capsule=0`）
- 对比：白板内嵌要加载 4.27 MB bundle（`article-app.js:660-679`），导图只需一个 iframe

## 四、数据流设计

```
写文章（Vditor）
  └ 工具栏「插入白板 / 导图」→ 选择已有 or 新建 → 光标处插入 fence
       ```embed board:wb-abc123
       ```embed map:mm-xyz789 :h=520 :caption="登录流程"

保存 → 纯 Markdown 文本进 content（**零新增字段，数据模型不动**）

阅读（article.html）
  └ Markdown 渲染（两条管线已统一）
      └ renderer.code 识别 ```embed → 输出占位容器
           <div class="embed-block" data-embed="board:wb-abc123" data-h="480">
  └ 统一挂载层 mountEmbeds(container)
      ├ board: → React 直挂（复用现有 mountExcalidrawEmbeds 逻辑 + 懒加载）
      └ map:   → iframe /mindmap.html?note=xxx（复现成页面）
  └ 失败/缺失 → 占位提示（引用的画布被删了不能白屏）
```

**核心设计思想：把挂载从「解析层」解耦到「DOM 扫描层」。**

理由是现有 `mountExcalidrawEmbeds(container)`（`article-app.js:633-657`）已经证明这条路径可行，并且已经接进了两条渲染主流程：

- 整篇渲染完成后：`article-app.js:443`
- 分章每加载一章后：`article-app.js:263`

泛化它比重写解析器安全得多。同时这样能让 Worker 路径只需要「产出占位容器」，挂载语义完全由主线程负责——**两条管线的分歧被压缩到最小**。

## 五、必须同批修复的前提（3 项）

调研挖出的现存问题。**不修的话，新功能会「看起来做了但没生效」**：

### 前提 1：索引补 `mapId`（同时修掉一个现存 bug）

`admin.ts:360-376` 写入索引的 meta 只到 `boardId`：

```ts
const meta: ArticleMeta = { ..., boardId }   // ← 没有 mapId
```

而 `ArticleMeta` 接口声明了 `mapId`（`admin.ts:40`），记录里也存了（`:313`）。

**后果链条**：

1. `GET action=articles`（列表）返回的是索引（`admin.ts:224`）→ 列表里导图文章的 `mapId` 恒为 `undefined`
2. `admin-app.js:851` 的去重 `(ar.data||[]).find(a => a.type==='mindmap' && a.mapId===currentMapId)` **永远匹配不到**
3. → **每次点「发布」都会新建一篇导图文章，而不是更新同一篇**（`:858-860`）

白板没这个问题，因为 `boardId` 写进了索引。**两者不对称纯粹是漏写一个字段。**

**动作**：索引 meta 补 `mapId`；顺带核对 `ArticleMeta` 声明与实际记录的字段差异（接口写 `date`/`update`，记录写 `createdAt`/`updatedAt`，`admin.ts:28-29` vs `:314-315`）。

### 前提 2：统一 Markdown 解析管线

**动作**：让 Worker 路径与主线程一致。

推荐做法：把 renderer 逻辑抽成可在 Worker 中 `importScripts` 的独立文件，两条路径共用；或退一步——**Worker 只做纯解析，embed 的识别与挂载全部移到主线程的 DOM 扫描层**。

后者更稳，因为解析层产出的是字符串 HTML，无法携带挂载时机 / 懒加载 / 失败降级语义。

**验收**：一篇 6000+ 字的文章，内嵌白板与 `==高亮==`、图片灯箱均正常工作。

### 前提 3：删除 `mindmap` 的连带清理缺失

`admin.ts:405-421` 的 DELETE 分支只处理 `chunked`（清分块）与 `whiteboard`（连删 `excalidraw` 快照），**对 `type==='mindmap'` 没有任何清理** → 导图数据成为孤儿。

另：`mindmap.ts:191-204` 的导图 delete 也不清白板 files 空间（导图节点图片借用的是白板的 file 存储，`editor.ts:891`）→ **导图删了图片会残留**。

**动作**：DELETE 分支补导图清理；导图 delete 补图片清理。

## 九、风险与踩坑清单

1. **Worker 路径丢 renderer（最大坑）**：见前提 2。现有白板内嵌已在踩。
2. **分章切点 vs 内嵌块**：`splitChapters()` 只按 `^#{1,2}` 切（`admin.ts:111`），单章过大时再按空行切。fence 是多行结构，**需要验证跨章边界不会被切断**。
3. **分章文章主记录 `content === ""`**（`admin.ts:334`）：任何「读单篇直接解析 content」的新代码路径会拿到空串。`article-app.js:89` 靠 `d.chunked` 分流才没出问题。
4. **画布形态文章的 `content` 是空串**：文章页目录、字数、评论、AI 上下文（`article-app.js:50`）在纯白板/纯导图形态下拿不到内容。若将来要做「全文搜索 / AI 问答」，需要先把画布内容物化成可索引文本（导图可用转换器，白板基本不可能）。
5. **CDN 缓存叠加**：公开读走 `s-maxage=5, stale-while-revalidate=120`（`admin.ts:217`），前台另有 `sessionStorage` 30 分钟（`article-app.js:70`）。改数据结构后前台可能长时间看到旧内容，排查时别误判成「代码没生效」。
6. **`renderBoardCard` 是死代码**（`app.js:326-357` 无调用方）、`.card-board` / `board-chip` 无样式、**`article-embed` 概念全仓 0 命中**。**不要基于这些「看起来存在的抽象」设计。**
7. **`window.eeSetType` 全仓未定义**（`admin-edit.js:291` 是唯一引用）→ 给普通文章绑导图**不会真的变成导图文章**。若第三期要做「文章转导图形态」，这里得先补实现。另注意 `collect()` 提交的 `type` 来自 `docType`（`:760-761`），改 `doc.type` 不会改 `docType`。
8. **`mind-elixir` 未登记进 `package.json`**（只在 `node_modules` 中存在）→ 新机器 / CI 上 `pnpm i` 后导图构建会失败。建议补登记。
9. **历史版本语义两边不一致**：白板快照 key 用被覆盖的 `existing.rev`（`excalidraw.ts:386-389`）且创建时 `rev=0`；导图用 `nextRev`（`mindmap.ts:290-293`）且创建时 `rev=1`。做统一版本 UI 时「回滚到第 N 版」会差一版。
10. **留言有两套命名空间**：文章留言 postId = 文章 id（`article-app.js:47`）；白板/导图 = 画布 id（`editor.tsx:683`、`editor.ts:415`），且画布形态会隐藏整块评论区（`article-app.js:1049-1057`）。混排文章正文里内嵌导图时，导图自己的留言挂在导图 id 上——**需明确这是否符合预期**。

## 十、待确认的次要细节

1. **内嵌块的留言入口**：内嵌导图/白板的「留言」是否要在块浮条上提供？现有实现是导图/白板页内自带抽屉（走 `postMessage` 唤父页，`article-app.js:569-571`）。混排文章里，块级留言和文章评论可能让读者困惑。
2. **`:title=` 参数是否必要**：画布自身有标题（`notes/<id>/meta` 的 `title`），内嵌块是否还要单独覆盖。
3. **内嵌块在 RSS / 分享链接里的降级**：`feed.xml` 是静态生成的，内嵌块在 RSS 阅读器里会变成什么（大概率是子串文本）——需要确认是否要在 RSS 里替换成提示文案。

## 附录：被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 用 `boardId` / `mapId` 数组表达混排 | 需改数据模型与索引结构；且 Vditor 只输出 Markdown，正文里的引用天然该在正文里 |
| 用自定义 HTML 标签（`<div data-embed>`）做标记 | Vditor wysiwyg 模式会把 HTML 当内容/转义，`getValue()` 取回的 Markdown 不干净 |
| 用图片语法 `![白板](excalidraw:demo)` | Vditor 里会显示成裂图，写作体验差（`docs/讨论.md` 约 426-431 行已记录） |
| 导图内嵌走 bundle 懒加载（照搬白板） | 导图 bundle 是首屏硬加载且无懒加载路径，改造成本高于直接用 iframe |
| 文章 ↔ 导图双向同步 | 导图节点 id 会重新生成，按文本 diff 回写会丢备注与图片锚点（见第六节） |
| 内嵌导图原地编辑 | 会让文章页变成第二套编辑器，与 `#view-mindmap` 功能重复 |
