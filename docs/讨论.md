# 写博客功能改进讨论

## 问题描述

当前写博客部分（admin.html 中的写文章界面）存在以下问题：
- 界面元素太多：标题、摘要、标签、封面图、图片管理等一堆表单干扰写作
- 不适合沉浸式写作体验

## 用户需求

| 需求 | 描述 |
|------|------|
| 极简模式 | 进入写作页只看到标题+编辑器，其他设置折叠或延后填写 |
| 延后设置 | 摘要、封面图、标签等发布时再填，不要一开始就显示 |
| 沉浸式编辑 | 像 Notion/Typora 那样，标题和正文一体化，没有分离的表单 |
| 轻量编辑器 | 替换 Toast UI Editor，使用更轻量的编辑器 |

## 讨论记录

### 2026-09-04 第一次讨论

**编辑器选择：**

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| Milkdown v6 | 所见即所得，Notion 体验 | 需要打包工具，纯静态 HTML 无法直接使用 | ❌ 放弃 |
| Vditor | CDN 友好，支持所见即所得/即时渲染/分屏预览，国人开发 | 非 Milkdown | ✅ 选择 |
| 保留 Toast UI | 已有集成 | 太重，界面复杂 | ❌ 放弃 |

**最终选择：Vditor**
- 支持三种模式：所见即所得、即时渲染（类似 Typora）、分屏预览
- CDN 友好，有 UMD 构建，无需打包工具
- MIT 协议
- 支持 Markdown 扩展语法（思维导图、流程图等）
- 内置代码高亮
- 支持图片上传

**发布流程：**

| 方案 | 描述 | 结论 |
|------|------|------|
| 发布时弹窗填写 | 点发布按钮后弹出弹窗填写标签、封面等 | ✅ 选择 |
| 侧边栏折叠 | 侧边栏收起，点展开后填写元数据 | ❌ |
| 草稿→发布两步 | 先保存草稿，发布时才填写完整信息 | ❌ |

**页面结构：**
- 改造现有 admin.html 中的写文章部分（而非独立页面）

# Excalidraw 集成到博客讨论

> 开始时间：2026-09-04 ｜ 项目仓库：https://github.com/excalidraw/excalidraw
> 目标：把 Excalidraw 白板集成进本站（纯静态 HTML + Netlify Functions + Blobs），实现"笔记 → 存储 → 展示 → 协作"闭环。

## 需求拆解

| 需求 | 含义 | 对应 Excalidraw 能力 |
|------|------|---------------------|
| ① 内置到博客 | 在博客里直接打开/使用白板编辑器 | npm 包 `@excalidraw/excalidraw`（React 组件），官方有 [集成文档](https://open-source.gitbook.io/excalidraw/docs/integration) |
| ② 存储到 Blobs | 画完自动/手动保存到 Netlify Blobs，随时续画 | 场景数据 = `elements[]`(JSON) + `appState` + `files`(图片)；通过 `onChange` / `updateScene` 读写 |
| ③ 截图放博客文章 | 把笔记转成图片插进 Markdown 文章 | `exportToBlob()` / `exportToSvg()` 导出 PNG/SVG，走现有 `/api/upload` |
| ④ 笔记做成博客页面 | 笔记有公开只读页面，甚至做成独立"博文" | `viewModeEnabled` 只读模式；或导出静态 SVG/PNG 直接嵌入 |
| ⑤ 允许别人改笔记 | 公开协作编辑（可实时，可非实时） | 官方实时协同后端**不开源**；自托管需 Yjs + WebSocket（见下） |

## 现状与约束

- 本站前端为**无框架原生 JS**（Vditor 等均靠 CDN/vendor 静态引入），无 React、无前端构建链；
- 后端为 Netlify Functions v2 + `@netlify/blobs`，已有统一封装 `_shared/blob.ts`（KVStore：get/set/delete/list），本地开发回退 `.local-data/`；
- 已有图片上传链路 `/api/upload`（base64 → Blobs → `/images/c/*.png`），可直接复用于"截图入库"；
- Excalidraw 是 React 组件库，纯 `<script>` 引入需要 UMD 构建（官方仓库曾修过 UMD 可在浏览器直接用 [#7349](https://github.com/excalidraw/excalidraw/pull/7349)），且依赖 React（官方 issue 多次提到与新版 React 的兼容摩擦 [#7895](https://github.com/excalidraw/excalidraw/issues/7895) [#9253](https://github.com/excalidraw/excalidraw/issues/9253)）。

## 关键技术要点（调研结论）

1. **数据格式**：一张白板 = `elements`（矢量元素 JSON）+ `files`（嵌入的图片/二进制，`{id:{mimeType,dataURL}}`）。全部可序列化后存 Blobs 单个 key，尺寸一般几百 KB～几 MB，Blobs 无压力；建议 JSON 整体存取、保留版本号。
2. **编辑 API**：`<Excalidraw initialData={{elements, appState, files}} onChange={...} />` + `excalidrawAPI`（`updateScene`、`getSceneElements`、`exportToBlob` 等）足够实现"载入→编辑→保存→导出"。
3. **只读展示**：官方 `viewModeEnabled` 只读模式可做交互式白板页；纯静态场景（SEO/无 JS）用导出 PNG/SVG 即可。
4. **实时协作**：官方 excalidraw.com 的 live collaboration 后端私有，无法自托管；社区通行做法是 **Yjs + 自建/托管 WebSocket**（如 excalidraw-yjs-starter 类项目：elements 同步进 Yjs 文档）。Netlify Functions 是无状态函数，不适合长连接 —— 实时协同需要一个**独立常驻服务**（小 VPS / Fly.io / Railway / 托管 y-sweet）。
5. **非实时协作（重要替代）**：不追求"同时光标"，用 Blobs 做"共享存储 + 保存冲突检测 + 版本历史"，任何人打开同一笔记都能改、保存即更新、可回滚。**完全跑在现有 Netlify 基础设施上，零额外服务器**，能覆盖绝大多数"别人帮我改笔记"场景。

## 方案选项

### A. 嵌入方式

| 方案 | 做法 | 优点 | 缺点 | 倾向 |
|------|------|------|------|------|
| A1 官方 UMD + React 18 UMD | 下载 `excalidraw.production.min.js` + React 18 UMD 到 `public/js/vendor/excalidraw/`，页面直接引 | 无构建步骤，与博客现状一致 | React 19 已无 UMD；官方对 UMD 非一等支持；版本升级要重下文件 | ⚠️ 可行但脆弱 |
| A2 本地打包一次（推荐） | 新增 `scripts/build-excalidraw.ts`（esbuild），把 React + Excalidraw 编辑器打成 1-2 个静态 bundle 提交进 repo，页面照常 `<script>` 引入 | 可控、可定制 UI、可拆"编辑器/只读"两个 bundle；构建一次后部署无需构建链 | 首次引入 esbuild + React 依赖 | ✅ |
| A3 iframe excalidraw.com | 博客内嵌官方站点 | 零开发 | 数据在官方服务器，无法打通自家 Blobs，不满足需求② | ❌ |

### B. 存储与接口

- 新增 `netlify/functions/excalidraw.ts`（路由 `/api/excalidraw`）：
  - `PUT  {id, scene}` 保存场景（带 `revision` 版本号，旧版入 `revisions/{id}/{ts}` 供回滚）
  - `GET  ?id=` 取场景
  - `GET  ?id=&list=1` 取笔记列表（Blobs `list({prefix})`）
  - `DELETE`（可选，需 Admin-Key，复用现有 `auth.ts` 模式）
- 复用 `getBlobStore("excalidraw")` 即可，本地开发自动落 `.local-data/`。

### C. 页面形态（先做哪个取决于用户偏好）

1. **独立笔记页**：`excalidraw.html?note=xxx` —— 编辑器+保存；`excalidraw-view.html?note=xxx` —— 只读展示页（可转发给别人的"公开笔记链接"，也是"笔记博客化"的载体）；
2. **文章内嵌**：markdown 里插入特殊标记（如 `![excalidraw](note:xxx)`），文章渲染时把只读画板/SVG 渲染进正文 —— 需求③④的"截图放博客"；
3. **发布为博文**：保存时一键导出 PNG 上传 + 自动生成 Markdown 草稿（正文里嵌图+链接到可编辑原文）—— 需求④"做成一个博客"。

### D. 协作等级

| 等级 | 能力 | 需要 | 结论 |
|------|------|------|------|
| L1 共享编辑（非实时） | 公开链接可改，保存即更新，可回滚 | 仅现有 Netlify 栈 | ✅ 首选落地 |
| L2 实时协同 | 多人同时画、光标可见 | 独立 WebSocket 服务（Yjs），成本与运维 | 🔜 二期可选 |
| L3 官方房间辅助 | 临时用 excalidraw.com 实时协作 | 官方站点 | 数据不回自家库，仅应急 |

### E. 安全与防滥用（公开可编辑必须考虑）

- 保存冲突：`revision` 乐观锁，他人已更新则提示"取最新/覆盖/另存"；
- 版本历史 + 一键回滚（Blobs 存历史快照，成本低）；
- 编辑开关：管理员可把某笔记设为"只读/可编辑"，或编辑需输入口令（放 URL 参数或简单密码字段）；
- 滥用防护：保存限流 + 内容大小上限（如 ≤2MB），参考现有 upload 的防护写法。

### 2026-09-04 第一轮结论（已拍板）

| 问题 | 决策 |
|------|------|
| 嵌入方式 | **A2 本地 esbuild 打包**：新增 `scripts/build-excalidraw.ts`，用 esbuild 将 React + `@excalidraw/excalidraw` 打成静态 bundle 提交进 repo，页面普通 `<script>` 引入 |
| 笔记博客化形态 | **两者都要**：文章正文可内嵌可交互白板（Markdown 特殊标记 → 渲染时替换）；一键"发布为普通博文"（导出 PNG 插图 + 自动生成草稿） |
| 协作等级 | **L1 共享编辑**：公开链接可编辑、保存即更新；架构预留 Yjs 接入点，二期评估 L2 实时 |
| 编辑安全 | **版本历史 + 一键回滚**（每次保存留快照）；**编辑需口令**（只读公开，编辑要口令）；**每篇笔记可切换只读/可编辑** |

**由此锁定的产品形态：**
1. 独立编辑页 `excalidraw.html?note=xxx`（可选口令解锁编辑）—— 画完自动/手动保存到 Blobs；
2. 独立只读页（公开链接，可转发）—— 笔记"博客化"第一形态，也是 L1 协作的只读入口；
3. Markdown 内嵌标记（如 `:::excalidraw note=xxx`）→ 文章正文渲染为可交互白板；
4. 「发布为博文」：导出 PNG → 走 `/api/upload` 存图 → 生成带图+原文链接的 Markdown 草稿进后台。

**后端接口草案（下一轮细化）：** `netlify/functions/excalidraw.ts` → `/api/excalidraw`：
- `GET ?id=` 取场景（公开）；`PUT {id, scene, editKey}` 保存（校验口令）；
- `GET ?id=&history=1` 版本列表；`POST ?action=rollback` 回滚（需 Admin-Key）；

### 2026-09-04 第二轮细化结论（设计定稿）

**1. 前端 bundle 架构：单 bundle、双模式（不拆 editor/view）**

**3. 数据模型与 API 定稿**

Blobs store 名 `excalidraw`，key 结构：

| key | 内容 |
|-----|------|
| `notes/{id}/meta` | `{ title, editable: 0|1, editKeyHash, createdAt, updatedAt, rev }`（Admin 可写） |
| `notes/{id}/scene` | 当前场景 `{ type:"excalidraw", version, elements, appState 白名单子集, files }` |
| `notes/{id}/rev/{rev}` | 保存前快照（rev 递增整数，保留最近 50 份） |
| `notes/{id}/files/{fid}` | 预留：超大 files 拆 key 存储（二期） |

API（全部并入 `netlify/functions/excalidraw.ts`，`config.path = "/api/excalidraw"`，已与 Functions v2 路由风格对齐）：

| 方法/路径 | 权限 | 说明 |
|-----------|------|------|
| `GET ?id=` | 公开 | 返回 scene + meta 公开字段（editable/hasKey/title/updatedAt） |
| `PUT ?id=` | 公开+口令 | 新建：无口令直接创建；已存在：`editable=1` 且（无口令或口令 hash 匹配）→ 先写 `rev/{rev+1}` 快照再覆盖 scene，rev/updatedAt 递增 |
| `POST ?id=&action=rollback&rev=N` | Admin-Key | 快照恢复（写回 scene + 历史保留） |
| `POST ?id=&action=meta` | Admin-Key | 改 title / editable 开关 / 重设口令 |
| `GET ?action=list` | Admin-Key | 笔记列表（管理页用） |

files 策略（本期）：整体 JSON 存 scene，上限 8MB（PoC 已实现）；单张嵌入图 >1MB 时保存提示压缩；拆 key 懒加载二期做。
权限体系与现有 `_shared/auth.ts`（X-Admin-Key）对齐；口令存 SHA-256 hash 不落明文。

**② 大场景优化：透明 gzip 压缩（替代 files 拆 key 方案）**
- 拆 key 存储在此场景收益低（笔记总是整张读取、Blobs 无单 key 硬限制），真正瓶颈是 PUT 请求体体积 → 改为**前端 gzip 压缩传输 + 后端透明解压存储**；

- 后端：`compressed=1` 路径 gunzip 解压（上限：压缩文本 16MB / 解压 50MB 防 zip bomb）→ 校验 JSON → 以 `g1:` 前缀存储；GET 时透明解压返回；快照/回滚天然兼容（存的是存储原文）；

- 回归测试 24-31 项：压缩体积 <1/3、压缩创建/读回 2000 元素、落盘 `g1:` 格式、压缩更新、回滚往返、清理。

**③ L1.5 协作感知（无需外部服务的"近实时"）**
- 后端 `GET ?metaOnly=1`：只返回 meta（rev/editable/hasKey），轻量轮询端点；
- 前端轮询：view 模式每 20s、edit 模式每 30s 检测 meta.rev 变化：
  - view：**自动静默刷新**（`updateScene` 增量替换，不闪屏不重置视图）；
  - edit：提示「检测到他人更新」，不打断本地编辑（避免覆盖未保存改动），可刷新页面查看；
- 说明：Netlify Functions 无 pub/sub、Blobs 无事件，SSE 长连接不可行，轮询是现有栈内最优解（每请求 ~1KB，开销可忽略）。

# 博客多内容格式讨论（2026-09-04）

> 需求：文章不止 Markdown 一种形态——纯白板文章（无目录）、普通文章（有目录）、
> 卡片笔记（轻量小记录）、未来更多自定义页面。现提出内容类型化方案。

## 现状

- 文章统一实体：Blobs 文章（`id/title/tags/excerpt/image/content/wordCount/status` + 索引），渲染管线唯一：article.html 取 content → marked 渲染 → 目录/高亮；
- 「白板文章」目前只是普通文章 + ```excalidraw fence（有目录区域，且依赖 Markdown 包装）；
- 首页文章列表统一卡片；无类型区分。

## 核心建议：内容实体增加 `type` 字段（枚举，向后兼容）

| type | 含义 | 阅读页形态 | 备注 |
|------|------|-----------|------|
| `article` | 普通 Markdown 文章（默认） | 正文 + 目录（现状） | 现有文章不填 = article |
| `whiteboard` | 纯白板文章 | 整页交互白板，**无目录侧栏** | 正文区直接挂 Excalidraw view |
| `card` | 卡片笔记（二期） | 卡片流 / 轻量展开，无完整阅读页 | 标题+几句话+标签 |

**改动点（小）**：
- `admin.ts`：POST articles 接受并透传 `type` 进存储与索引（meta.type 缺省 article）；列表接口原样返回；
- 前端列表/管理：type 只做展示徽标（「白板」「卡片」），排序/分页逻辑不变；
- 机制天然可扩：以后加「链接收藏」「问答」等只加枚举与渲染分支。

## 白板文章（P1 优先）

**数据**：type=whiteboard + `boardId`（Excalidraw 笔记 id）；content 可留空或放一句话简介；image 放自动导出的封面 PNG（列表卡用）。

**阅读页**（article.html 按 type 分支）：
- whiteboard：跳过 marked/目录/高亮管线；**隐藏整个 tocSidebar**（当前"无标题时空态"升级为按类型整块隐藏）；正文容器 `<div class="article-whiteboard" data-excalidraw data-note=boardId data-mode="view">` 复用懒加载 view 渲染；
- 布局可全宽（无侧栏时正文区加宽）。

**创建闭环**：
1. Excalidraw 编辑器「发布为博文」升级为**发布选型**（普通文章草稿 / 纯白板文章）；
2. 后台白板管理页增加「发布为文章」操作（任一笔记 → 生成 whiteboard 文章草稿，自动导出封面）；
3. 纯白板文章 URL 仍走 `article.html?post=..&blob=..`（统一列表/评论/导航），只是渲染不同。

**目录与导航**：whiteboard 无 tocSidebar；上/下篇导航保留；评论区保留（可留白板讨论区）。

## 卡片笔记（P2 建议）

**数据**：复用文章库 `type=card`（自带索引/标签/评论基建），content 为短文（≤500 字建议），不生成完整阅读页。

**展示**：
- 独立归档页 `/notes.html`：卡片瀑布流（glass 卡片 + 标签筛选 + 时间线感）；

- 点卡片展开（详情浮层/原地展开），不跳独立详情页（保持轻量）；需要长文再转正为 article。

**录入**（轻量优先）：
- admin 新增「卡片」tab：一行标题 + 多行内容 + 标签，随写随存（类似快速记录）；
- 也可以从文章管理把草稿降级为卡片。

| 形态 | URL | 说明 |

# 前台页面重新设计讨论（白板文章页 / 卡片笔记页）

> 目标：这两个前台页面要与普通博客文章页**形态完全不同**，建立独立的产品气质。

## 一、纯白板文章阅读页 → 「沉浸式画布空间」

**设计概念**：普通文章 = 文档（纸面阅读）；白板文章 = 作品（进入"展厅"看一张画）。打开白板文章就像打开一张可交互的大画布，页面本身消失，只剩画布与悬浮的玻璃控件。

**布局（桌面端）：**

```
┌────────────────────────────────────────────────────────────┐
│  ◐ 悬浮玻璃胶囊导航（极简，可自动隐藏）                        │
│  [← 返回]     标题 ……                        [✎ 编辑] [信息] [评论] │
├────────────────────────────────────────────────────────────┤
│                                                            │
│            ┌──────────────────────────────┐                │
│            │                              │                │
│            │       白板画布（整屏舞台）      │    ← 场景底色，     │
│            │     （自带缩放 / 平移 / 适应）   │       中心画布居中  │
│            │                              │                │
│            └──────────────────────────────┘                │
│                                                            │
│                                   [上一张]       [下一张]     │  ← 左右悬浮箭头
└────────────────────────────────────────────────────────────┘
    （右侧可滑出：评论抽屉玻璃面板）
```

**与现在（文章壳里塞白板）的本质差异：**

| 维度 | 现状（文章壳） | 重新设计（画布空间） |

### 2026-xx 写文章页白板改为 iframe 内嵌（解决整页只剩编辑器浮层）

**现象：** 在写文章页点「白板」后，整个页面只剩下白板编辑器的浮层（看起来像一个弹窗），后台其它内容全部不可见。

- wbMount 改为 iframe 内嵌**独立白板页**：/excalidraw.html?note=<id>&edit=1
  - 与后台样式、脚本、布局完全隔离，后台的侧边栏/顶栏/按钮都正常显示
  - iframe 内自带编辑器顶栏与「保存（Ctrl+S）」
  - 发布时的画板保存通过同源桥接调用 iframe 内的 __excalidrawSave（新增 boardSaver() 助手）
- wbReset 直接清空 iframe（等价于彻底卸载，无残留监听）
- setWriteMode('board')：无画板则自动新建一块并挂载；有画板但未挂载则恢复
- 编辑页（白板文章）的白板同样改为 iframe 内嵌（.ee-frame + 保存桥接），去掉直接挂载与 bundle 手动加载

### 2026-xx 修复白板保存 413（请求体超 6MB）：内嵌图片逐张单独存储

**现象**：保存白板时 PUT /api/excalidraw?id=xxx 返回 **413**（另有若干 metaOnly 轮询 ERR_CONNECTION_CLOSED，以及字体慢加载的 Intervention 提示，属网络层噪音）。画布改动没能存下来。

**原因**：Netlify Functions 单次请求体上限约 6MB，超限会在进入函数前直接被拒。画布里**贴的图片是 base64 内嵌**在场景 JSON 里的（Excalidraw `files` 字段），gzip 对已压缩的图片数据几乎无效——编辑器虽已有压缩（>400KB 触发），压缩后仍可能远超 6MB。

**修复（bundle v15）**
- 后端 `excalidraw.ts` 新增 `action=file`：GET / POST / DELETE 单张图片，存 `notes/<id>/files/<fid>`；单张 dataURL 上限 5.2MB 字符；写权限与场景保存一致（管理员，或笔记对外可编辑且无口令）；删除笔记时随 `notes/<id>/` 前缀一并清理
- 编辑器保存：先从 `api.getFiles()` 逐张上传**有变化**的图片（每张一个请求，体积远低于上限），场景 JSON 不再内嵌图片数据，只保留 `fileIds` 列表；图片指纹（长度 + 末尾片段）存在 ref 里，未变化则跳过，避免每次保存重传
- 编辑器加载：读场景后按 `scene.fileIds` 逐张拉回图片合并成 `files`；旧数据（仍内嵌 files）直接使用，且**不记录指纹**——它们还没单独存过，首次保存必须上传，否则会只剩 id 而图片缺失
- 体积预检：压缩后仍超过 5.2MB 时提前提示「画布数据过大，服务器单次请求上限约 6MB，请拆分画板或减少元素」，不再盲目撞 413
- 压缩阈值从 400KB 降到 64KB（更早压缩，减少体积）
- 恢复 Excalidraw 自带导出菜单（`export: {}`、`saveToActiveFile: true`）——顶栏移除后用户需要能导出 .excalidraw 备份（注意 `export` 的类型是 `false | ExportOpts`，不能传 `true`，否则 tsc 报错）
- bundle 版本 v14 → v15，并**同步全部 4 个引用点**：excalidraw.html（3 处）、article-app.js（EXC_BUNDLE_VERSION）、admin-app.js（2 处）、admin-edit.js（EXC_BUNDLE_VERSION）

### 2026-xx 白板保存再提速：二进制直传 + 参数下调 + 耗时诊断（bundle v18）

**背景**：上一版（v17，压缩 2000px/0.85）后用户反馈"还是很慢"——需要判断卡在压缩、上传还是场景本体。

## 2026-02-14 批次：大纲显示与编辑手感

### 问题
1. 大纲面板里二级、三级写不出来（或被压平）。
2. 写大纲要手敲 "- " 和缩进，很累。

### 根因
大纲解析是「一级 = 缩进 2 空格」的硬映射，而且**第一行只要带缩进或 "- "，后面所有行的层级就整体错位**（旧代码只把首行强行当根、其余按绝对缩进算），于是单空格缩进、粘贴的 Markdown 列表、Tab 缩进全都被压成一级。解析本身没错，是容错太差。

### 改法
- 解析重写为「相对层级」：缩进（2 空格或 Tab 一级）、Markdown 列表符（- * + 1. 1)）、# 标题三种写法都认；层级跳级时逐级回退找父节点，不再丢行；首行无论带不带前缀都当中心主题。
- 导出保持「根行无前缀，其余 2 空格 × 层级 + - 」，往返稳定（7 组用例全部通过）。
- 编辑手感新增：
  - 回车 → 自动在下一行补同级缩进和 "- "，直接接着写；在空节点上回车则删掉前缀并退回上一级。
  - Tab / Shift+Tab → 当前行降级 / 升级，前缀自动跟着变。
  - 单独输入 "-" 自动补空格。
  - 光标停在空节点前缀后按退格，一次删掉整段前缀。
- 面板提示改为「回车自动接下一项 · Tab 降级 · Shift+Tab 升级 · 改动实时成图」。

## 2026-02-14 批次：胶囊溢出与编辑开关

### 1. 编辑切了但导图动不了（真 bug）
根因：MindElixir 5 的编辑权限是**实例属性 mind.editable**，库内部到处是 if (!e.editable) return（点节点不进编辑、右键菜单不弹、按键不增删）。上一版我只做了 DOM 层拦截，从没打开这个开关，所以胶囊切成了编辑态、工具条也出来了，但导图改不动。

- 显示条件原来限定「文章页 iframe 嵌入且非后台」，独立打开导图页时没有返回。现在放宽为「非后台嵌入」：文章页嵌入走 postMessage 通知父页面回首页，独立打开直接 location.href = "/"。后台 iframe 内不显示（顶栏已有返回入口）。
